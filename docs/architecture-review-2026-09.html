2. Collapse the auto-start seam: one adapter is hypothetical

Worth exploring

AutoStartManager.swift  ·  AutoStartServiceRepresentable protocol

Before — extra adapter layer

StatusViewModel
AutoStartManager
AutoStartServiceRepresentable (protocol)
SystemAutoStartService → SMAppService

One real adapter. MockAutoStartService exists only for tests — a hypothetical seam.

After — seam at the right level

StatusViewModel
AutoStartManager (deep) → SMAppService direct

Delete AutoStartServiceRepresentable + SystemAutoStartService. Restore only when a second real adapter appears.

Problem

AutoStartServiceRepresentable has exactly one real adapter. By the one-adapter rule this is a hypothetical seam — adds interface width without real leverage.

Solution

Delete the protocol and wrapper class. AutoStartManager holds SMAppService directly. Inject closure-based test doubles per operation.

Wins

  • delete 2 shallow modules
  • interface shrinks; depth stays
  • no seam to misread as a variation point

3. Extract the status-message derivation into a StatusPresenter

Worth exploring

StatusViewModel.swift (lines 83–121)  ·  StartupRunCoordinating.swift (StartupRunState)

Before — two statics + inline transition guard

sink { state in
self.remainingDelays = state.remainingDelays
self.networkStatus = deriveNetworkStatus(from:state)
if state.phase != .idle || self.previousPhase != nil
|| self.statusMessage == "Ready" { ← magic string
self.statusMessage = derivedMessage
}
self.previousPhase = state.phase
}

After — pure StatusPresenter value type

sink { state in
let display = presenter.derive(state, managedApps)
self.statusMessage = display.message
self.networkStatus = display.networkStatus
self.remainingDelays = display.remainingDelays
}

Problem

The previousPhase transition guard is inlined in the sink closure with a silent dependency on the magic string "Ready" matching the init default. Renaming the default silently breaks the guard.

Solution

Extract a StatusPresenter value type: pure function (StartupRunState, [ManagedApp], Phase?) → StatusDisplay. All transition logic moves inside it. Tests hit it directly — no view-model setup needed.

Wins

  • magic string dependency eliminated
  • locality: all status-text logic in one place
  • tests hit StatusPresenter directly
  • inline previousPhase mutation disappears from subscriber

4. Deepen AppPreset: hide preset resolution behind the store seam

Speculative

AppPreset.swift  ·  ManagedApp.swift (isDiscord)  ·  ManagedAppStore.swift  ·  AppInspectorSheet.swift

Blast radius

The sub-agent confirmed that isDiscord is referenced in five places: ManagedApp (computed var), ManagedAppStore.load() (migration), StatusViewModel.addApplication() (status message), AppInspectorSheet (UI label), and AppPreset.knownPresets (truth source). The parallel tracks are an active maintenance hazard: a new Discord bundle ID only needs adding in one place (AppPreset.knownPresets) but currently must also be updated in ManagedApp.isDiscord.

Problem

ManagedApp.isDiscord duplicates identity logic that AppPreset.knownPresets already owns. Three independent callers branch on it. Adding a third Discord bundle ID would require editing both ManagedApp and AppPreset.

Solution

Delete isDiscord from ManagedApp. Let addApp(at:) return (app: ManagedApp, note: String?). AppPreset produces the note; callers display it without knowing why.

Wins

  • single source of preset identity
  • new App Presets need no changes outside AppPreset
  • ManagedApp becomes pure data

Additional findings — full sub-agent read

Sub-agent finding

A research sub-agent independently read every Swift source and test file. These findings were not captured in the primary candidates.

F1 — PopoverPresenting casts through its own abstraction

Worth exploring

StatusItemController.swift L37–L42

Production code downcasts PopoverPresenting back to NSPopover to set the content view controller. If a mock is passed, the content VC is silently never set. The abstraction is one-directional: only tests benefit; production always requires the concrete class. Fix: add func setContentViewController(_ vc: NSViewController) to PopoverPresenting, or acknowledge that the protocol shouldn't abstract NSPopover at this level and replace it with a simpler closure-based test double.

F2 — networkStatus is a stringly-typed contract

Worth exploring

PopoverContentView.swift L123–L132 · StatusViewModel.swift

PopoverContentView.networkStatusColor switches on the exact string values published by StatusViewModel.networkStatus. Changing "Network connected" to "Connected" silently breaks the colour logic with no compilation error. Fix: publish a NetworkStatusLevel enum (.connected, .waiting, .skippedOffline) alongside or instead of the string. The View drives colour from the enum; the string is display-only.

F3 — launchResolvedApp silently swallows errors

Strong

StartupRunCoordinator.swift L404

try? await self.windowSuppressor.launch(app: app) — errors during a Startup Run launch are discarded. launchImmediately (the test-launch path) correctly propagates. A workspace refusal, entitlement denial, or WindowSuppressionEngine failure becomes a silent no-op during boot with no user feedback. Fix: capture the error, update StartupRunState with a per-app failure enum, surface it in the managed apps list.

F4 — isAppAlreadyRunning is untested as a unit

Worth exploring

StartupRunCoordinator.swift L376–L397

Three matching heuristics: bundle identifier (case-insensitive) → bundle URL → last path component. The third is aggressive: any app whose last path component is Steam.app would be blocked. The bundle-ID heuristic is exercised by the integration test skipsAlreadyRunningApps; the URL and name-match paths are never directly tested. Fix: extract isAppAlreadyRunning as a pure static function taking a [RunningAppRepresentable] parameter; add dedicated unit tests for each heuristic.

F5 — No composition root: wiring is duplicated across three inits

Speculative

StatusViewModel.init · StartupRunCoordinator.init · StatusItemController.init

Each init has a "create if nil" fallback pattern. The dependency graph is rebuilt implicitly from three different sites. StatusViewModel acts as an accidental composition root for its children, which is subtle. If you want a single shared WorkspaceManaging instance you must know to inject it explicitly, or accept two SystemWorkspaceManager instances. Fix: explicit AppDelegate composition root that constructs the full graph and injects concrete instances. Low urgency while the app is single-window.

F6 — addDirectlyForTesting leaks test infrastructure into production

Worth exploring

ManagedAppStore.swift L114

addDirectlyForTesting is internal and used in 5+ test files. Test infrastructure lives in the production type. Fix: replace with a dedicated init that accepts a pre-populated [ManagedApp] array, or factor the method into a test-only extension file inside the test module using @testable import.

F7 — AppDelegate reaches two levels deep to kick off launch

Speculative

AppDelegate.swift L12

statusItemController?.viewModel.startStartupRun() — AppDelegate crosses two ownership levels to call a method on a grandchild. This is a mild seam violation: AppDelegate knows the shape of the view model. Fix: add a start() method to StatusItemController that internally calls viewModel.startStartupRun(). AppDelegate becomes unaware of ViewModel.

F8 — SuppressionEpisodeBudget mutation is a value-type footgun

Speculative

WindowSuppressionEngine.swift L209–L226

SuppressionEpisodeBudget is a value type stored in a class-owned dictionary. Mutating it requires the caller to write back: entriesByAppId[appId] = entry. If that line is ever omitted, the episode is silently discarded. Currently correct. Mitigation: make GuardEntry a class (reference type) so mutations propagate without the write-back, or add a comment flagging the invariant.
